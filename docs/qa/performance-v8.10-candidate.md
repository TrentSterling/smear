# Unpublished work after V8.9

The live release is still V8.9 (`998a9f8fff66f3dbe5897a8b428e5c09f57d2118dee0d2c922be088d104ba352`). These are candidate measurements, not a release receipt or completion of the performance objective. The pending Chromium recovery change must not ship while its preservation gate fails.

## Audio

The native Chromium audit measured 39.6 ms in `AudioContext` construction on first Spill input. Preparing the existing graph during loading removes that constructor call from input. Sound generation and scrape automation remain locked until a native gesture. The graph still processes audio during profiling; every owned browser independently mutes its output.

Both [Chromium](v8.10-candidate/audio-chrome.json) and [Firefox](v8.10-candidate/audio-firefox.json) pass seven lifecycle checks: one loading-time graph, silent continuous layers before input, no transient voices from pre-input simulation, native unlock of the same running graph, enabled noise/tone synthesis, five transient-node disconnections after sounds end, and no browser errors. No synthesis recipe or gameplay RNG changes.

## Transfer and queue pressure

Dispatch bounds now cover the commands in the dispatched batch rather than future queued commands. A fully clipped skin mark produces no bitmap or RGBA readback. The previous region calculation could invert its bounds and make `getImageData` throw. Adaptive small batches were rejected: they reduced individual transfers but failed throughput, reached the queue cap, and fell back to the main thread.

Chromium's default single accelerated worker is the transfer reference. Merely starting its bitmap promises concurrently did not help: the tested transfer mean was 58.8 ms versus 31.7 ms sequentially. A candidate packs changed regions into reusable, bounded atlases and creates one bitmap per atlas. WebGL uploads original regions using source-row selection, resetting skip and row-length state afterward. Shared bitmaps close only after every patch has been presented or discarded.

On the same fixed Chaos workload, the [sequential transfer](v8.10-candidate/bitmap-sequential.json) averaged 31.75 ms per job, with 3,657 peak queued events. The [atlas candidate](v8.10-candidate/bitmap-atlas.json) averaged 10.24 ms, with 1,201 peak queued events. Main-thread means were 7.05 and 7.19 ms; this is a transfer/queue improvement, not an isolated total-CPU speedup. Physics, wet transfer, droplet state and particle matrices matched exactly. Five persistent surface pixels changed by at most two premultiplied levels. Therefore the strict PNG-equality comparison failed, although the existing GPU pigment tolerance passed. Repeating the unchanged sequential reference produced identical pigment and a 233 ms overload frame, so those five pixels are not dismissed as reference nondeterminism.

The transfer-only [native atlas run](v8.10-candidate/native-atlas.json), before adding cooperative mirror recovery, kept the worker through Spill, pistol, drag and Chaos. Chaos measured 60.03 FPS, 6.82 ms mean work, 11.1 ms p99 and 28.4 ms maximum. The earlier native candidate reached synchronous fallback with a 285.7 ms Chaos frame. Host pressure differed; these are individual native traces, not a deterministic end-to-end speedup. Audio was enabled, unlocked, running and output-muted throughout.

## Recovery remains under investigation

Retaining a Canvas2D mirror permits bounded Chromium recovery without WebGL `readPixels`, and fixes failure immediately after graphics restoration. Cropped DOM-canvas uploads are required during accelerated recovery. Repeated `getImageData` uploads changed tiny-pigment accumulation in the 12,000-event burst test; that version was rejected. Hard-cap pressure now accumulates dirty bounds for the next presentation task instead of uploading after every forced command.

The current cooperative atlas version passes [84 worker lifecycle checks](v8.10-candidate/worker-atlas-lifecycle.json), including clipping, failure after partial presentation, clear/wash/removal races, graphics loss, all batches actually in flight, and a 12,000-event burst. Every case checks zero WebGL pigment readback and bounded resources. This smaller lifecycle suite passing does not override the failing complete starvation comparison below.

The [forced atlas starvation trace](v8.10-candidate/starvation-atlas-candidate.json) reduced worst main-thread work from [320.6 ms](v8.10-candidate/starvation-atlas-v8.8.json) to 35.3 ms under approximately 99% host load. This is **not a passing preservation result**: [eleven surface pixels exceed the existing two-level tolerance](v8.10-candidate/starvation-atlas-pixel-differences.json), maximum ten. Skin differences remain within two levels. The exact pigment assertions and their thresholds were not widened. Neither cooperative atlas recovery nor the older experimental Chromium RGBA recovery is ready to become the release default.

An [isolated replay probe](v8.10-candidate/recovery-raster-probe.json) captures the published reference's exact pigment prefix and 4,134 outstanding commands, then replays them in a worker. Both default and explicitly accelerated recovery canvases keep every pixel within one premultiplied level of contiguous main-thread reference replay. Forcing software rasterization produces 115,845 pixels outside tolerance and a maximum delta of 53, so that backend is rejected. This isolated result motivated the threaded replay implementation described below; it was not itself a complete starvation pass.

The original 120 Hz physics, nine solver passes, bristles, contact spacing, 900-drop pool and rendering resolution remain intact. Catch-up physics, adverse host scheduling and complete Chromium recovery preservation remain open. Candidate receipts retain their individual source fingerprints; no claim is made that every experiment tested the current final working-tree bytes.

The [native Firefox capture](v8.10-candidate/native-firefox.json) retains audio enabled and running throughout. The queue fills, 8,009 recovery events remain at the end, and catch-up physics averages 6.65 ticks per frame. This is not a proof that native Chaos stays fast under heavy contention, nor an eight-millisecond bound.
## Threaded recovery checkpoint

Worker-owned backlog replay is now integrated into the candidate. Canonical pigment seeds are prepared across bounded tasks; replay retains each record's worker affinity and command order. Completed records update their mirrors before their event logs are trimmed. Ordinary batches stay at 1,024 events, the normal queue stays at 4,096, and the combined outstanding recovery log stays at 8,192. Normal worker failures retain a recovery worker pool for future painting. A first overload can adopt that pool as the replacement normal pool. The hard cap still invokes the foreground safety path when no worker can consume the backlog.

At source `004966acced20275f84ef07b5482739d32ed77524e8b2a6495dedf791bfdd43d`, [Firefox](v8.10-candidate/worker-threaded-firefox.json) and [Chromium atlas](v8.10-candidate/worker-threaded-atlas.json) each pass all 94 lifecycle checks. They cover every surface and skin, exact state/wet transfer, the unchanged two-level pigment tolerance, zero WebGL pigment readback, failure after partial presentation, clipping, clear/wash/removal, overload, restart, graphics loss and the 12,000-event hard-cap burst. Cases that do not exhaust the hard cap execute zero replay commands on the main thread.

The [complete Firefox starvation comparison](v8.10-candidate/starvation-threaded-firefox.json) passes all six strict assertions: both queues actually reach 4,096, all 419 intervals are retained, simulation/wet transfer match exactly, every surface/skin PNG matches exactly, the worst work frame falls by more than threefold, and there are no browser errors. At nearly 100% host load, the old worst frame is 1,709 ms and the candidate is 471 ms. Mean work worsens from 49.9 to 62.0 ms in that run; passing the worst-frame gate is not proof of acceptable frame rate. It hits the 8,192 recovery cap and executes 31,444 replay commands in the foreground.

The earlier [threaded Chromium starvation trace](v8.10-candidate/starvation-threaded-atlas-candidate.json) cuts worst work from [382.2 ms](v8.10-candidate/starvation-threaded-atlas-v8.8.json) to 24.0 ms, but [six surface pixels remain outside tolerance](v8.10-candidate/starvation-threaded-atlas-pixel-differences.json), maximum ten. Its strict persistent-pigment assertion still fails. Those results are retained as a failure, not replaced by the smaller passing lifecycle suite.

Native Firefox with sound enabled, unlocked and running remains unacceptable under saturation. The [threaded native trace](v8.10-candidate/native-threaded-firefox.json) records 6.42 FPS Chaos, 139.54 ms mean work and 249 ms maximum at approximately 100% host pressure. It reaches the recovery cap, returns to foreground raster, and ends with 7,813 pending events. Physics catch-up averages 8.62 ticks per frame. Reusing the existing workers during overload avoids rebuilding their pigment but the [first retained-worker trace](v8.10-candidate/native-retained-firefox.json) still hits the hard cap and records 5.92 FPS Chaos. Worker retention alone is not a demonstrated fix.

`?paintKeepWorkers=1` is an opt-in overload experiment that retains healthy workers and their already rasterized pigment instead of terminating them. `?paintStreamRecords=1` additionally sends completed RGBA records as they finish, instead of waiting for the entire worker reply. Logs are retired only after the main thread presents those pixels and commits its canonical mirror. All workers remain bounded to one input batch, and a final reply acknowledges the full job. These experiments are not release defaults. The combined [Firefox retention/streaming lifecycle suite](v8.10-candidate/worker-retained-stream-firefox.json) passes all 94 checks, including both overloads, partial-presentation failure and graphics restoration. It verifies zero foreground replay outside hard-cap pressure, bounded queues and the unchanged pigment tolerance. Native performance and full starvation comparisons remain separate gates.

The release remains V8.9. No physics threading, tick reduction, solver reduction, particle-cap reduction, paint-density reduction or rendering-resolution reduction has been introduced. The overall goal remains active: native overload, complete Chromium pigment preservation, and main-thread physics catch-up are unresolved.

The [native retention/streaming Firefox run](v8.10-candidate/native-retained-stream-firefox.json) still fails the practical performance target: Chaos averages 3.84 FPS, 224.81 ms mean work and 619 ms maximum at 100% host CPU pressure. The cap forces 13,507 foreground replay commands and leaves 7,911 outstanding events. Streaming is correctness-verified; it is not a demonstrated native saturation fix and remains opt-in.

The same checkpoint's [native Chromium trace](v8.10-candidate/native-threaded-atlas-chrome.json) averages 57.85 FPS Chaos, 9.57 ms mean work and 90.2 ms maximum. It also reaches the hard cap and executes 17,559 foreground replay commands before recovering. Sound runs throughout both captures and output stays independently muted. Main-thread CPU samples identify texture uploads, pigment readback, the coupled physics step and collision/contact processing; the full sampled profile remains in the ignored native output directory. Chromium's better average does not override its failing pigment comparison or the remaining hitch.

An isolated [Firefox accelerated-raster native input](v8.10-candidate/native-accelerated-raster-firefox.json) requests `willReadFrequently:false` without changing release defaults. It uses verified hardware WebGL but still reaches the cap: Chaos averages 9.89 FPS, 88.35 ms mean work and 253 ms maximum. Canvas2D options are hints; this is not proof that its paint rasterizer actually used the GPU. The [Firefox replay isolation probe](v8.10-candidate/recovery-raster-probe-firefox.json) replays the same 4,134 events over 23 records with default, false and true options; all three produce zero differing pixels. Changing the context hint alone is therefore neither a demonstrated performance solution nor a pigment regression in that probe.

## Coupled simulation worker prototype

The generated architecture probe in `tools/simulation-runtime.mjs` moves the unchanged coupled solver, contact damage, wet transfer and droplet simulation into one worker. The foreground retains the real renderer, camera input, HUD and running WebAudio graph. It is a separate generated HTML under ignored `tools/out/`; `index.html` and the published release have not been replaced. Moving a solver slice alone would defer contact callbacks that influence later solver passes, so this probe executes the complete coupled step.

[Chromium](v8.10-candidate/simulation-worker-chrome.json) and [Firefox](v8.10-candidate/simulation-worker-firefox.json) each pass 18 checks over 7,200 paired ticks. All six original scenarios retain exact body state, velocities, contact forces, wet state, droplets, every ordered paint command and every ordered audio recipe. The pool adds checks for every surface and skin PNG against the existing pipeline, retaining the two-level premultiplied tolerance. [Firefox passes all 24 pool checks](v8.10-candidate/simulation-pool-firefox.json).

Painting everything in the simulation worker initially kept rendering smooth but failed simulation throughput. The [direct-raster Firefox trace](v8.10-candidate/simulation-direct-native-firefox.json) renders Chaos at 60.02 FPS while executing only 113.40 ticks/sec. This is not an acceptable performance result. The separate painter pool retains four Gecko raster workers, one in-flight batch per painter, 1,024-command batches, a combined 8,192-command bound and sixteen versioned dirty regions per record. Painting backpressure waits in the simulation worker rather than invoking foreground raster. Presentation retains one latest cumulative patch per record, closes superseded bitmaps and acknowledges the actual raster revision. Region history is retired only after acknowledgement, so replacing a pending patch cannot discard earlier pigment.

The [native Firefox pool trace](v8.10-candidate/simulation-pool-native-firefox.json), at 3,000 by 1,800 with audio enabled, unlocked, running and output muted, records:

| Workload | FPS | Simulation ticks/sec | Foreground mean | Foreground p99 / maximum |
|---|---:|---:|---:|---:|
| Spill | 60.00 | 119.82 | 2.00 ms | 4 / 4 ms |
| Pistol | 60.00 | 119.75 | 3.49 ms | 6 / 10 ms |
| Soaked drag | 59.99 | 119.82 | 3.22 ms | 5 / 9 ms |
| Chaos | 59.83 | 119.71 | 6.21 ms | 10 / 12 ms |

Chaos peaks at 1,118 outstanding pigment commands. There is no foreground replay. This is a substantive native result, not completion of the eight-millisecond objective. The callback-entry histogram still includes a 32 ms maximum gap. Simulation throughput comes from authoritative step counters over measured wall time, not from presentation FPS. The earlier native Firefox capture predates the prototype's F3 step-counter bridge, so its histogram's zero foreground ticks does not describe the worker's actual tick rate.

The [native Chromium RGBA pool trace](v8.10-candidate/simulation-pool-native-chrome-rgba.json) holds 60.00 FPS / 119.82 ticks/sec in Chaos, with 3.60 ms mean foreground work, 7.9 ms p99 and 9 ms maximum. It remains rejected: [the full pigment comparison fails](v8.10-candidate/simulation-pool-chrome-rgba-failure.json) on one boundary-scenario surface pixel, maximum six levels. Returning Chromium to one ImageBitmap painter retains simulation and ordered recipes, but [two boundary pixels still exceed tolerance](v8.10-candidate/simulation-pool-chrome-bitmap-failure.json), maximum 2.988 levels. These failures are preserved; no tolerance or workload was reduced to obtain a pass.

One isolated Firefox launch stalled before the driver returned a session. Its [failure receipt](v8.10-candidate/simulation-native-launch-timeout.json) contains no performance samples and is not counted as a pass. Cleanup verified the exact owned harness and Firefox profile before terminating only that process tree. The subsequent complete native capture above ran successfully. All GPU/browser runs were sequential.

Production integration remains outstanding: parent shader pigment comparisons, complete inspection/API behavior, failure and graphics-restoration lifecycle, live worker telemetry, and all seventeen release harnesses. The later [stopping checkpoint](threaded-checkpoint.md) implements foreground canonical canvas inspection, authoritative state, asynchronous API commands and reset/demo camera handling, with 22 actual bridge checks on Firefox. Chromium pigment preservation is unresolved. The live game remains V8.9; the user requested a remote checkpoint followed by a halt.

The [final native Firefox probe](v8.10-candidate/simulation-pool-native-firefox-final.json), after removing unused worker GPU-instance preparation and adding the worker/step telemetry bridge, retains 60 FPS in Spill, pistol and soaked drag. Chaos drops to 57.18 FPS / 116.66 ticks/sec, with 6.20 ms mean foreground work, 33 ms p99, 42 ms maximum and a 57 ms callback gap. Worker scheduling discards 156 ms under the inherited 75 ms elapsed-time clamp. Peak outstanding pigment is 3,336, with no foreground replay. This later trace is not replaced by the earlier better result; remaining render/upload and scheduling spikes still fail the practical performance objective. The final Firefox pool source still passes all 24 preservation checks.
